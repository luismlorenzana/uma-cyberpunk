## Implementation

1. Inventory the existing launch routes, pack parser, quest and scene gates, save stores, owner API and PWA cache. Record which runtime and publisher pieces carry forward and which older tier code serves legacy routes.
2. Define one private catalog of actors, homes, capitals, fixed duos, roles, ship templates, expeditions, targets and finale outcomes. Preserve shared identity and art handles. Validate exactly two Umas from one system, their two distinct Generals and their six distinct lieutenants for each duo. Validate one capital per system.
3. Implement a versioned campaign graph and compiler with ancestry, scoped outcomes and readable blocked reasons. Include executable required actor, participant, mission, location and result links. Print one inventory of route, portrait, environment and sprite coverage.
4. Add the fresh campaign identity to launch, API, account guard, save, device DB and PWA cache. Resolve default selection per release and carry old inputs through existing rules where they remain in use. Start the new timeline with the game's real premise and one routable sign-on.
5. Verify parser limits and full data size. Particular areas include max encounter lists, state/flags, release JSON exports, file dependencies, pins, cast identity references and the high-population profile. Plan lazy loading and storage on measured evidence.
6. Contract the operation eligibility surface with CY84–CY89 so one policy owns UI and write checks. Reserve fields for named release, local and global readiness, ordering, branch commits and frozen mission inputs.

## Done when

A new profile can open the correct campaign and reach its real opening, distinct from older installed profile data. A contract check rejects duplicate members, cross-system pairs, duplicate capitals, invalid actor hull/role combinations, cyclic prereqs and impossible branch/orphan results. Exact starting Story and Art source revisions are recorded. No old campaign progress is required for release.
